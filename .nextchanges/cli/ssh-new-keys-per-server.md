* `databricks ssh connect` now writes the client key pair to the session's secret scope and generates a new server host key each time it starts an SSH server, instead of reusing the keys already in the scope. Hosts configured by `databricks ssh setup` keep using the client key in their local key file. Known limitation: two servers started for one session at the same moment can leave the scope with one server's host key and the other server's metadata; clients then refuse to connect until the wait for the server times out, and running `databricks ssh connect` again recovers. ([#8090](https://github.com/databricks/cli/pull/8090))
